# alia-plugin-team

Команды агентов по ролям для [VesnALIA](https://getbb.app): руководитель планирует и
принимает работу, исполнители (разработчик, младший разработчик, тестировщик,
писатель и другие) отчитываются ему. В проекте может быть несколько команд,
команды создаются из шаблонов.

English version: [README.md](README.md).

## Установка

```bash
alia plugin install git:https://github.com/kirei4ik/bb-plugin-team.git@^0.2.0
# или для разработки — из локальной папки:
alia plugin install /путь/к/alia-plugin-team
```

## Быстрый старт

Через панель **Team** в навигации:

1. Панель показывает все проекты тремя группами — *с командами*, *можно
   создать команду*, *сейчас нельзя создать* (с причиной), — по алфавиту и с
   поиском сверху.
2. Откройте проект, выберите шаблон, поправьте роли, провайдеров и модели и
   нажмите **Создать команду**. Роль с выключенным провайдером блокирует
   создание.
3. Команды проекта показываются деревом: руководитель → исполнители →
   помощники. В каждой строке — статус, модель и текущий пакет работ. Клик по
   строке открывает действия: открыть тред, написать, выдать пакет, остановить.

Через CLI (в треде проекта или с `--project`):

```bash
alia team init --team core --template dev   # .vesnalia/teams/core.yaml + промпты ролей
alia team doctor --team core                # провайдеры, окружения, промпты, git
alia team create --team core                # создать треды
alia team status                            # все команды проекта
```

## Команды, файлы и git

| Что | Где |
|---|---|
| Конфиг команды | `.vesnalia/teams/<команда>.yaml` (старый `.vesnalia/team.yaml` = команда `main`) |
| Промпты ролей | `.vesnalia/teams/<команда>/<роль>.md` |
| Держит команду вне git | `.vesnalia/teams/.gitignore` |

Новые команды по умолчанию **не версионируются**. `alia team version on --team core`
(или галочка в панели) включает хранение в git, `off` выключает. Если корневой
`.gitignore` игнорирует весь `.vesnalia/`, сначала замените строку на `.vesnalia/*` и
`!.alia/teams/` — плагин об этом подскажет.

Названия тредов задаёт настройка **формат названия**, по умолчанию
`👥 {team} · {role}`; имя команды не пишется, пока в проекте одна команда. У
каждой команды своя секция в сайдбаре (`Team`, `Team · qa`).

## Шаблоны

Встроенные: `dev` (руководитель, разработчик, младший разработчик на дешёвой
модели, тестировщик — по умолчанию, настроен на качество кода при малом
бюджете токенов), `qa`, `docs`, `product` (менеджер, аналитик, писатель).
Шаблоны общие для всех проектов сервера:

- Настройки → Team: редактирование, дублирование встроенных, новый шаблон из
  видов ролей с готовыми промптами.
- CLI: `alia team template list | show | save | delete`;
  `save <id> --kinds lead,developer,junior,tester`, `--from-team core`,
  `--from-template dev`.
- Панель: **⋯ → Сохранить как шаблон** у команды.

В Настройки → Team шаблон по умолчанию выбирается из списка. Встроенные и
сохранённые шаблоны показывают одинаковую форму; встроенный сначала нужно
дублировать. Для ролей используется селектор провайдера и модели VesnALIA;
сохраняются модель, уровень рассуждений и service tier. Недоступная сохранённая
модель не заменяется автоматически. Стартовый промпт можно вставить без вызова ИИ.
Отдельный выбор модели черновиков пока только сохраняет настройку генератора.

После смены языка подписи общих настроек обновятся после явного
`alia plugin reload team`.

Роль без `prompt`/`promptFile` получает короткий встроенный промпт своего
вида `kind` (lead, developer, junior, tester, reviewer, writer, analyst,
devops, manager; `developer-2` считается `developer`).

## Работа с командой

```bash
alia team task add developer "Форма входа" --note "критерии" --send   # пакет с учётом
alia team task update 3 --status review --review '{"result":"Готово", "checks":[{"what":"Smoke","result":"пройден"}]}'
alia team task done 3 --reason "Критерии выполнены" --expected-submission <id-отчёта>
alia team tell tester --message "перезапусти smoke"   # или all
alia team add-role junior --provider pi --model qwen3
alia team add-role reviewer --thread thr_…      # взять свободный тред проекта
alia team pause [--stop] / alia team resume
alia team stop [<роль>|all]
alia team replace developer [--keep]        # новый тред с передачей дел
alia team report --out "$ALIA_THREAD_STORAGE/team.html"   # сводка для чата (inline-vis)
alia team retitle                           # применить формат названий заново
```

- **Помощники**: тред, созданный под тредом команды, становится помощником
  этой роли.
- **Пауза** придерживает сообщения агентов и плагина исполнителям; сообщения
  человека не задерживаются.
- **notifyOn: [idle, error]** у роли будит руководителя после её ходов.
- `alia team create` можно запускать повторно: он создаёт только недостающие
  роли и заново привязывает исполнителей, потерявших руководителя.

## Beads и ручная смена сессии

Трекер выбирается **для проекта целиком**, для всех его команд и worktree.
Настройка в панели Team или `alia team tracker beads|builtin|default --project <проект>`
имеет приоритет над `defaultTracker` в настройках плагина. Дефолт — Beads.
`default` убирает проектное переопределение. Недоступность Beads — ошибка;
автоматического перехода на встроенный трекер нет. Старые встроенные пакеты
сохранены: для доступа к ним явно выберите `builtin`. Переноса карточек нет. Перед сменой трекера завершите пакеты и замените
отработавшие сессии на свободные: ссылки исполнения не переносятся между
трекерами. Закрепить уже выбранный трекер явно можно без смены сессии.

При создании команды Team готовит Beads в **основном checkout проекта**:
использует существующую базу или создаёт отсутствующую локальную базу через
`bd init --non-interactive --skip-agents --skip-hooks --stealth --init-if-missing`.
Режим `--stealth` не создаёт Git-коммит и не меняет индекс; локальные исключения
добавляются в `.git/info/exclude`. Повреждение
или недоступность базы не считаются её отсутствием. В worktree отдельная база
не создаётся; dry-run ничего не инициализирует.
Команды `bd` выполняются через host entry на хосте основного checkout, даже
когда исполнитель работает в другом worktree. На этом хосте должны быть `bd`
и Git. Ошибки отсутствующего CLI, базы или недоступного хоста видны пользователю.

В таблице задач Team колонка «Назначена роли» показывает `assignee` из Beads.
В CLI назначение можно посмотреть через `bd show <id>`, а задачи роли —
`bd list --assignee <роль>`.

Задачи Team в Beads помечены `alia-team:<имя-команды>`, assignee — имя роли.
Существующую задачу можно явно назначить через
`bd update <id> --assignee <роль> --add-label alia-team:<команда>` в основном checkout.
Сохраняется её исходный строковый ID. Team читает описание, критерии, приоритет,
зависимости, решения и результат из Beads; редактирование `task update --note`
меняет description. Приёмка — `task done`, отмена — `task update --status dropped`.
Review хранится как `in_progress` с `alia-state:review`, отмена — `closed` с
`alia-state:dropped`. Не убирайте эти служебные метки при внешнем редактировании.

Одна сессия исполняет один пакет. Перед `review` исполнитель сохраняет содержательный
checkpoint. После приёмки Team автоматически заменяет завершённую сессию, когда
есть следующая готовая задача и окончены все операции. Без готовой задачи новую
сессию не создаёт. Без актуального checkpoint ждёт его сохранения; при
неоднозначном сбое требует проверки человеком. В новой сессии очередь учитывает
зависимости Beads. `review` удерживает роль до приёмки руководителем.
Связанные исправления того же пакета продолжаются в его сессии.

Перед заменой сохраните JSON-файл с состоянием работы, например:

```json
{
  "goal": "Завершить страницу профиля",
  "criteria": ["Сохранение профиля проходит проверку"],
  "progress": "Форма готова, осталось проверить сохранение",
  "decisions": [{"what": "Сохранить текущую ветку", "why": "В ней незавершённые изменения"}],
  "checks": [{"what": "Целевой тест", "result": "Пройден"}],
  "blockers": [],
  "nextAction": "Проверить сохранение в интерфейсе",
  "files": ["src/profile.ts"]
}
```

Затем:

```bash
alia team checkpoint <id> --file /абсолютный/путь/checkpoint.json --project <проект> --team <команда>
# Дождитесь завершения активного хода и фоновых операций.
alia team replace <роль> --project <проект> --team <команда>
```

Пустые массивы допустимы, обязательные поля должны присутствовать. Размер
checkpoint — до 64 KiB; встроенное хранилище также имеет общий лимит KV 256 KiB.
Команда дописывает environment ID, путь, ветку, коммит и fingerprint изменений,
сохраняет checkpoint в задаче и проверяет чтение обратно. Для ещё не начатого
готового пакета checkpoint фиксирует начало исполнения в текущей сессии.
У руководителя тоже должна быть задача координации и checkpoint.

`replace` сохраняет прежнее окружение и незакоммиченные файлы. Он отказывает
при активном ходе, фоновых операциях, ожидающих сообщениях/взаимодействиях,
неполном или устаревшем checkpoint, отсутствующем окружении. Нужен Git checkout
с HEAD; dirty submodule требует отдельной передачи. Дети с неизменяемым
`lifecycleOwnerThreadId` старой сессии пока блокируют замену.

Новый тред создаётся с начальным промптом, удерживаемым в очереди ядра VesnALIA
через `message.dispatch`. До завершения переключения роль не исполняется;
затем Team освобождает уже существующий запрос, не создавая повторную отправку.
При сбое освобождения выполните `alia team resume`. Статус `pending` допустим
только при единственном запросе, удерживаемом именно Team.

Содержание checkpoint хранится только в выбранном трекере (Beads:
`metadata.aliaTeamCheckpoint`), Team хранит технические ссылки и историю сессий.
В handoff не загружаются последний ответ или история прежней беседы.
Сообщения адресуйте через `alia team tell <роль>`, для руководителя доступен
псевдоним `lead`. Старые сессии не должны получать новые поручения.

При частичном сбое выполните `alia team doctor`, затем
`alia team replace <роль> --dry-run --json`: состояние передачи содержит старый
и новый ID. Обычный повтор `replace` продолжает передачу без второго spawn.
Если роль ещё не переключилась, `replace <роль> --abort` отменяет передачу,
возвращает детей и сохраняет старую сессию. После переключения нужно завершить
передачу повтором, отмена запрещена. Если ответ spawn потерян, можно явно
подтвердить найденный тред с удерживаемым промптом через `replace <роль> --thread <новый-id>`;
проверяются его проект, окружение и метки передачи. Первичный промпт остаётся одним запросом в очереди VesnALIA; его не нужно
отправлять повторно. Состояние старого протокола с неопределённой доставкой
требует проверки нового треда перед ручной отправкой.

Готовность к приёмке уведомляет руководителя. Блокировки и запросы решения
передавайте через `alia team tell lead`; ошибки исполнения уведомляют его отдельно.
`notifyOn: [idle]` остаётся явным выбором, а не обязательным пробуждением после
каждого хода. При внешнем изменении зависимостей очередь можно повторно
проверить существующей командой `alia team resume`.

Проверка без вызовов моделей: `npx vitest run acceptance.test.ts`. Этот сценарий
использует настоящие временные Git worktree и Beads, но тестовый VesnALIA SDK-хост;
он не доказывает живую работу UI/провайдера на установленном сервере.

## Закреплённые модели и самостоятельное планирование

Роли шаблона сохраняют `provider`, `model` и `reasoningLevel`. Настройка плагина
`defaultTemplate` выбирает шаблон при создании новой команды в панели и CLI;
явный `--template` имеет приоритет. Например, после сохранения шаблона
`ollama-cloud`: `alia plugin config team set defaultTemplate ollama-cloud`.
Это не меняет существующие команды. Отсутствующий выбранный шаблон нужно
исправить или явно заменить; скрытого перехода на другую модель нет.

Руководитель получает постоянные инструкции вести выбранный трекер по цели
обычным языком: критерии, порядок, зависимости и назначение ролям. Эпики нужны
для крупных целей. Спорные продуктовые приоритеты, границы и существенные
расходы уточняются у пользователя. Просьба обсудить или спланировать не разрешает
писать код. Политика добавляется и к пользовательскому промпту без изменения
файла и сохраняется после замены сессии.

## Передача длинной задачи

Исполнитель может сохранить состояние и запросить передачу собственной сессии:
`alia team checkpoint <id> --file <абсолютный-json-путь> --rotate`.
Запрос не обрывает текущий ход: Team ждёт окончания операций и продолжает тот же
пакет с прежним ID, окружением, веткой и незакоммиченными файлами. Руководителю
для такой передачи тоже нужна связанная задача координации.

На границе idle Team читает доступный показатель контекста кодом, без вызова
модели для измерения. Порог 80% применяется только к корректному показателю
с `estimated: false`. Нет показателя, лимита или есть только оценка — порог
не запускает замену; агент использует явный запрос `--rotate`. Проверенный Pi
в текущем окружении возвращает оценку. Неопределённый результат переключения
требует проверки человеком; новый spawn/send вслепую не повторяется.

### Состояние рабочей сессии в панели

В карточке сотрудника показаны текущий тред, связанная задача, точность данных о контексте, сохранённое состояние для передачи и причина ожидания. Просмотр и обновление карточки не вызывают модель. Кнопка «Сохранить состояние и сменить сессию» может запустить агента для подготовки checkpoint; текущие операции не прерываются. Без связанной задачи действие недоступно, для руководителя нужна задача координации. Приблизительные показатели контекста не запускают автоматическую смену на 80%.

### Приёмка и профили моделей

Приёмка и возврат требуют причины. Руководитель читает отчёт и передаёт его
`id` через `--expected-submission`: устаревший отчёт принять нельзя. Ручная
приёмка без отчёта отмечается отдельно. Возврат через `task update <id>
--status in-progress --return-reason "<замечание>"` доставляет замечание
исполнителю для продолжения той же задачи в том же окружении. Неопределённая
доставка — явная ошибка без автоматического повтора. Наличие отчёта само по
себе не доказывает выполнение проверок.

`executionPolicy` хранит подтверждённый пользователем список запасных моделей.
`noAdditionalCost: true` — подтверждение пользователя, а не проверка цены.
Незавершённые, неподтверждённые и повторяющиеся варианты сохранить нельзя.
При подтверждённой квоте резерв применяется только с пригодным checkpoint
и доступным независимым провайдером; иначе — явная остановка.

В карточке сотрудника «Резервные модели» редактирует профиль действующей роли
той же формой, что и шаблоны. Источник — конфиг команды. Шаблон копируется при
создании; последующие правки шаблона не наследуются. Пустой список означает
отсутствие резервов; основная модель берётся из роли (если не задана — из VesnALIA).
Устаревшая форма не перезаписывает новый конфиг. Сохранение переформатирует
файл и удаляет YAML-комментарии, о чём форма сообщает перед кнопкой. Новые и заменённые сессии получают
актуальные профили; руководитель — профили всех ролей. Старые сессии
автоматически не переписываются.

### Конечные попытки и общий бюджет

В панели «Ресурсы и попытки» задаются пределы. По умолчанию — 8 единиц работы
на задачу (допуски запусков + возвраты с ревью), 100 допусков на команду.
Учитываются lead, исполнители, helpers, system retry и прежние сессии.
Увеличение лимита с основанием не сбрасывает счётчики. После ошибки нужно
конкретное изменение подхода; оно сохраняется в выбранном трекере. Новая
карточка/модель/сессия не обходит исчерпанный бюджет незавершённой задачи.
Автоматическое закрытие/отмена исчерпанной задачи не снимает блокировку.
Нужна ручная приёмка с основанием или ручное решение по ресурсам; общий бюджет
команды при этом остаётся.
Активные операции не прерываются.

Можно ограничить минуты и сообщённые накопленные токены. Статистика токенов
неполная; неизвестное не считается нулём. Контекст и его стоимость сюда не
подмешиваются. Жёсткий денежный или внутритуровый token cap не гарантируется.
Внутренние запросы/retry провайдера могут быть недоступны. Явный Send-now в VesnALIA
обходит hooks по устройству VesnALIA; такой запуск учитывается после наблюдения.
Чтение панели/отчёта не вызывает модели.

Замена при квоте использует только подтверждённый список, каталог текущего
хоста и существующий checkpoint/replace. Host+ALIA-provider консервативно
считается общим пулом; известные общие providerKey сопоставляются по хэшам.
Исключения квоты общие для команд хоста; точную область аккаунта между
неизвестными провайдерами доказать нельзя. Обычный HTTP429, auth, 503 и
неоднозначная ошибка не запускают перебор моделей. Неизвестный reset требует
проверки; известный reset/allowed-состояние снимает исключение пула.
Отсутствующий/stale checkpoint, очередь операций, pending replacement или
неопределённый spawn/delivery останавливают передачу. Исчерпанную модель не
просят сочинить checkpoint. Ручное восстановление — через существующие
`alia team replace`/`alia team resume`, без автоматического повторного spawn/send.
Причины, фактическая известная модель и результаты/основания из трекера
показываются в панели и `alia team report`.

Автозамена при квоте поддерживает отказ в приёме следующего ввода при
подтверждённой истории запроса и checkpoint, покрывающем предыдущую работу.
Если ввод уже принят, после checkpoint были операции или история недоступна,
работа останавливается даже при совпадении Git: внешние эффекты так не
проверить. Перед ручным replace нужно проверить состояние. Сжатие и
повтор отредактированного сообщения также обходят message.dispatch по
устройству VesnALIA; абсолютный предел всех LLM-затрат не обещается.
